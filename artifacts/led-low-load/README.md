# 1 颗 / 3 颗 LED 小负载测试固件

2026-10-29：**已烧录、下载校验通过、Flash 回读一致，实机测试通过，用户已确认实际灯色和颗数正确。** 当前板内运行本小负载版本，最终状态为全灭。旧的完整 R 图案固件备份仍在 `artifacts/can-bringup/`。

本版本为单独构建，启用 `LED_LOW_LOAD_TEST=ON`，上电先将 256 颗灯全部清零。收到命令后仍发送完整 256 像素帧，使未选中的灯不会保留以前的颜色。亮度通道值为 16/255，单色输出。

CAN1，1 Mbps，正常模式，标准数据帧，ID `0x002`，DLC=1：

| 数据 | 输出 |
|---|---|
| `00` | 全部熄灭 |
| `03` | 仅第 1 颗红色，其余 255 颗熄灭 |
| `04` | 仅前 3 颗蓝色，其余 253 颗熄灭 |

`0x600` 请求 / `0x601` 原样回传诊断仍可用。本测试版本的 `03/04` 不显示完整 R 图案。

固件：`F072_CAN_1LED_3LED.hex` / `.bin` / `.elf`。构建输出 Flash=17,000 B，链接器 RAM=14,928 B（包含预留栈）。复用原 PWM 缓冲，没有另开 256 像素 RGB 数组。

在工程根目录重新编译：

```powershell
cmake -S . -B build/led-low-load -G Ninja -DCMAKE_BUILD_TYPE=Debug -DLED_LOW_LOAD_TEST=ON
cmake --build build/led-low-load -j 4
```

下载（板子连接恢复后执行）：

```powershell
STM32_Programmer_CLI -c port=SWD freq=1000 mode=UR -w artifacts/led-low-load/F072_CAN_1LED_3LED.elf -v -rst -run
```

验收：

```powershell
py tools/test_led_low_load.py --hold 5
```

验收脚本先核对板内 Flash 与专用小负载 BIN 一致，再执行“全灭 → 1 红 → 全灭 → 3 蓝 → 全灭”。逐步检查 CAN 回包、接收/命令/显示计数和 DMA 完成计数，并读取完整 PWM 缓冲反解 RGB 数据，确认只指定 1 或 3 个非零像素。实际亮灯颗数和颜色仍需要现场观察确认。

## 本轮实测结果

- 下载日志 `flash_verify.log`：`Download verified successfully`，目标电压检测 3.41 V（这是烧录时的单次读数，不是亮灯瞬态供电测量）。
- `flash_match.log`：从板内回读固件，与本目录专用 BIN 完全一致。
- `led_test.json`：全灭、1 红、全灭、3 蓝、全灭，共 5 个阶段全部通过。
- MCU 共收到 10 帧：5 个灯控命令、5 个诊断请求；诊断回复 5/5，错误计数为 0、ESR=0，队列丢弃为 0。
- 灯控命令计数=5，显示启动计数=4（第一次全灭时本来已为全灭，不重复输出）。DMA 完成计数=5，包含上电自动清零的 1 帧。
- 完整 PWM 缓冲解码：逐阶段非零像素数量精确为 `0、1、0、3、0`，颜色精确为低亮度红 `(16,0,0)` 或蓝 `(0,0,16)`，所有其他像素均为 `(0,0,0)`，末尾复位槽全为 0。
- 全过程 SWD 读取成功、core running，没有复现之前整幅图案测试时的 ST-Link 掉线。
- 用户现场确认：`全灭 → 1 颗红灯 → 全灭 → 3 颗蓝灯 → 全现在对了`。

因此，“CAN 盒子 → MCU 接收命令 → PWM/DMA 输出 → 灯板实际显示”在本小负载范围内已完成闭环验证。

灯板接入时曾出现“发送命令前能读 MCU，发送后 ST-Link 从 USB 消失且 CAN 无回包”。改为 1/3 颗低亮度后稳定，这支持继续检查与负载有关的供电压降、供电接线/接触和回流路径，但本次同时降低了数量和亮度、且重新插接过 ST-Link，不是仅改变单一变量的电源容量测试。尚未测量亮灯瞬态的 5V/3.3V 电压，不能据此断言电源额定容量不足。即使动态亮灯数量减少，整块灯板仍有静态耗电。
